# CHCars

Plateforme web de consultation et de vente de véhicules.

## Structure du dépôt

Monorepo à deux applications **strictement séparées** :

| Dossier  | Rôle                        | Stack                                                   |
| -------- | --------------------------- | ------------------------------------------------------- |
| `front/` | Application cliente         | Next.js 16 (App Router), React 19, TypeScript, Bootstrap (`react-bootstrap`) |
| `back/`  | API REST                    | Node.js, Express 5, TypeScript, TypeORM, MariaDB (10.11 LTS+) |

Ne jamais mélanger le code `front/` et `back/`. Le frontend communique **uniquement** avec l'API backend (jamais directement avec la base de données).

## Règles générales

- Tout le code est en TypeScript.
- Code simple, lisible, maintenable ; respect de SOLID quand c'est pertinent ; pas de duplication.
- Aucun secret dans le code : tout passe par des variables d'environnement. **Aucun fichier `.env*` n'est versionné** (contenu documenté dans `README.md` §2) ; les secrets vont dans `.env.<env>.local`, chargés en priorité par `env.ts`.
- **Environnements dissociés** : `development` / `test` / `production`, chacun avec sa base MariaDB, son utilisateur (`chcarsdev` / `chcarstest` / `chcarsprod`) et son fichier `back/.env.<env>`. `env.ts` charge le bon fichier selon `NODE_ENV`, ordre `.env.<env>.local` > `.env.<env>` > `.env`.
- Ne pas supprimer de code fonctionnel sans le signaler.

## Frontend (`front/`)

- Routage : App Router de Next (dossier `app/`). Pas de React Router.
- UI : Bootstrap via `react-bootstrap`. Éviter le CSS personnalisé quand une solution Bootstrap existe. Le CSS Bootstrap est importé une seule fois dans `app/layout.tsx`.
- Composants `react-bootstrap` interactifs → marquer `"use client"`.
- Code applicatif dans `front/src/` : `components/`, `layouts/`, `services/` (client API), `hooks/`, `context/`, `types/`, `utils/`. Alias d'import : `@/*` → `front/src/*`.
- Appels HTTP via `src/services/apiClient.ts` ; URL de l'API dans `NEXT_PUBLIC_API_URL`.
- Cache de lecture côté navigateur (`utils/queryCache.ts`, stale-while-revalidate) : `listingService.list` / `getById` passent par `cachedQuery` (requêtes identiques partagées, liste fraîche 30 s) et les pages publiques s'affichent d'abord depuis `peekQuery` (retour arrière / fiche ouverte depuis une carte instantanés) puis se rafraîchissent. `apiClient` vide tout le cache après chaque écriture réussie (sauf `/analytics`, `/favorites`, `/contact`), donc aussi à la connexion / déconnexion. Rien n'est stocké côté serveur.
- `front/AGENTS.md` est un bloc géré et régénéré par `next dev` — le committer tel quel.
- Adresse publique d'une annonce : `/<locale>/annonces/<id>-<titre-en-slug>` — toujours via `listingPath()` (`utils/listingPath.ts`). Seul l'id compte pour charger la fiche ; une adresse ancienne / erronée (ou l'id seul) est remplacée par la canonique via `history.replaceState` (pas de rechargement). `pageKey()` ignore les mots du slug pour la clé de page, le suivi de navigation et la mesure d'audience ; côté back, `parsePagePath` enregistre `/annonces/<id>`. Les écrans admin (`/admin/annonces/<id>/modifier`) gardent l'id seul. Aucune colonne en base.
- Confirmations (supprimer, annuler…) : **jamais `window.confirm`** — utiliser `ConfirmButton` (bulle ancrée au bouton : message + « Non » / action). Un élément annulé ou supprimé disparaît de la liste affichée.
- Bouton « Retour » global (`BackButton`, rendu par `MainLayout` sur toutes les pages sauf l'accueil et `/admin`) : page précédente de l'app (`router.back()`), sinon section parente — `NavigationTracker` compte les navigations internes (`utils/navigationHistory.ts`) et remonte en haut à chaque nouvelle page ; sur retour/avance de l'historique, il restaure la position de défilement qu'il a mémorisée pour cette page (chemin + filtres).
- Petits plus : badges « Nouveau / Faible km / Récente » sur les cartes (`utils/listingHighlights.ts`, calculés depuis l'annonce, 2 max) ; étoile des favoris avec éclat + compteur dans la barre (`FavoritesNavLink`) — visible aussi pour un visiteur : clic → connexion, retour sur la même page et annonce ajoutée (`utils/favoriteIntent.ts`, repris par `FavoritesProvider`) ; confettis + carte « Vendu ! » quand le paiement solde un dossier (`Confetti`, rendus via portail sous `<body>` — un ancêtre transformé fausserait `position: fixed`) ; recherche rapide admin Ctrl / ⌘ + K (`admin/CommandPalette.tsx`, pages de `admin/adminNav.ts` + annonces + dossiers de vente).
- Comparateur (`/<locale>/comparer`) : bouton « Comparer » (`CompareButton`) sur les cartes et la fiche, 3 véhicules max gardés pour l'onglet (`utils/compareStore.ts`, `sessionStorage` lu via `useSyncExternalStore`), barre flottante `CompareTray` (masquée en admin et sur le comparateur) ; la page rafraîchit chaque annonce et met en avant la meilleure valeur par ligne (prix, année, km, puissance). « Trouve ma voiture » (`/<locale>/trouver`) : 4 questions en tuiles → score d'affinité 0–100 par annonce publiée (`utils/carFinder.ts`, testé : budget 40, boîte 20, énergie 20, usage 20 ; suggestions ≥ 50, 6 max) ; accès depuis l'accueil et la page Annonces.
- Langues fr / en / nl (`src/i18n/`, `Dictionary = typeof fr`, admin en français uniquement) : la langue est le 1er segment de l'adresse. Une adresse sans langue est redirigée par `proxy.ts` vers la dernière langue affichée (cookie `chcars_locale`, 1 an, posé par `LanguageProvider` côté navigateur — pas dans le proxy, qui voit aussi les préchargements de liens), sinon la meilleure langue du navigateur (`negotiateLocale`, poids `q`, testé), sinon le français. Traduction automatique du navigateur désactivée (`<html translate="no">` + meta `google: notranslate`) : elle réécrit le texte géré par React (langues mélangées, plantages).
- Métadonnées (pages = composants client) : chaque section publique a un `layout.tsx` serveur `sectionMetadata(...)` (`src/i18n/metadata.ts`) → titre traduit « … · BrabusCars », canonique + `hreflang` fr-BE / en-GB / nl-BE / x-default (URL absolues depuis l'hôte de la requête) ; pages personnelles et `/admin` en `noindex`. La fiche annonce (`annonces/[id]/layout.tsx`) lit l'annonce côté serveur (`services/serverApi.ts` : `API_INTERNAL_URL`, posé à `http://back:4000/api` par le compose, sinon `NEXT_PUBLIC_API_URL` absolu, sinon `/api` de l'hôte ; délai 2,5 s, échec = titre générique) pour son titre, sa description et l'aperçu de partage (`og:image` = 1re photo).
- RGPD : pages `/<locale>/mentions-legales` et `/<locale>/confidentialite` (`LegalDocument`, textes fr/en/nl dans `src/i18n/legal.ts`, coordonnées depuis `GET /api/company` : `COMPANY_LEGAL_NAME`, `COMPANY_HOSTING`, `COMPANY_VAT_NUMBER`…) liées en bas de page — **à tenir à jour quand une fonctionnalité change les données collectées, les prestataires ou les durées**. Avis `PrivacyNotice` sous l'inscription, le contact et la réservation. Carte Google Maps du contact chargée seulement au clic (`chc-map-placeholder`) : aucune requête vers Google avant.
- **Boutons d'action toujours à droite**, aussi sur téléphone : rangée `d-flex flex-wrap justify-content-end` (secondaire avant principal, texte d'aide à gauche), bouton d'en-tête de page en `ms-auto` ; cellule d'actions des tableaux `chc-table-cards` = `data-label=""` (alignée à droite dans la carte). Exceptions : pages de connexion / inscription (bouton pleine largeur), modales (`Modal.Footer` déjà à droite).
- Durées en jours (admin) : jamais « 0 j » — `utils/dayCount.ts` (testé) : `sinceDays` (« aujourd'hui », « hier », « 12 j ») pour une ancienneté / une date, `durationDays` (« < 1 j ») pour une moyenne, `daysWord` pour l'accord jour / jours.
- Vérification : `npm run build` (le check TypeScript de Next utilise des types générés absents d'un `tsc` isolé).

## Backend (`back/`)

Architecture en couches : **Route → Controller → Service → Repository → Entity/DB**.

- `routes/` : définition des endpoints, branchement vers les controllers uniquement.
- `controllers/` : réception requête, validation d'entrée (zod), appel service, réponse HTTP. Pas de logique métier.
- `services/` : logique métier.
- `repositories/` : accès aux données via TypeORM. Pas de SQL brut dans controllers/routes.
- `entities/` : entités TypeORM.
- `middlewares/` : `errorHandler` (gestion centralisée), `notFoundHandler`, `authenticate` / `authorize` (+ `adminOnly`).
- `config/` : `env.ts` (chargement `.env.<env>` + validation zod), `data-source.ts` (TypeORM).
- `scripts/` : `createAdmin.ts` (`npm run create-admin [-- --super]`), seul moyen d'obtenir un compte `admin` / `super_admin` hors interface ; `resetMfa.ts` (`npm run reset-mfa -- --email=…`) supprime la 2FA d'un compte (réenrôlement à la connexion suivante).
- `utils/` : `ApiError`, enveloppes de réponse, `actor.ts`, `cookies.ts`, mappers de réponse.

### Rôles et accès

Hiérarchie : `user` < `admin` < `super_admin`. `authenticate` **relit le rôle en base** à chaque requête (le rôle du JWT n'est pas utilisé) : un changement de rôle prend effet immédiatement, et un compte disparu est rejeté en 401. `authorize(minRole)` vérifie un **rang minimal** (via `ROLE_RANK`), donc un `super_admin` passe partout où un `admin` est requis.

- **Visiteur (non connecté) & `user`** : consulter **uniquement les annonces publiées** — chaque annonce porte le nom de sa marque / son modèle / sa catégorie. `GET /api/listings` force `status=published` (et ignore `sellerId`) pour tout non-admin ; `GET /api/listings/:id` renvoie 404 sur une annonce non publiée. Un `user` gère en plus ses favoris ; l'inscription publique ne crée que des `user`.
- Les **référentiels catalogue ne sont jamais exposés hors administration** : `GET /api/brands`, `GET /api/categories`, `GET /api/car-models` — liste **et** détail — sont derrière `adminOnly`. Les filtres marque / modèle / catégorie de la page publique `/annonces` sont donc dérivés des annonces elles-mêmes, pas d'un appel aux référentiels.
- **`admin`** : + gérer tout le **catalogue** (marques, catégories, modèles, véhicules) et les **annonces** (dont leurs **photos**). Routes d'écriture protégées par `adminOnly`.
- **`super_admin`** : + gérer les **comptes** — `GET /api/users`, `PATCH /api/users/:id/role` (bascule `user` ⇄ `admin`), routes protégées par `superAdminOnly`. Ne peut pas changer son propre rôle ni celui d'un autre `super_admin` ; le rôle `super_admin` ne s'attribue jamais via l'API. Chaque changement effectif est journalisé (table `role_change_log`, même transaction) et consultable via `GET /api/users/role-changes` ; côté front, l'interrupteur passe par une modale de confirmation. `DELETE /api/users/:id` supprime **uniquement un compte `user`** (jamais un admin, ni soi-même) : favoris en cascade, historique conservé, annonces éventuelles (ancien admin) réattribuées au super_admin.
- Côté front : `useAuth()` expose `isAdmin` / `isSuperAdmin` ; `AdminGuard` protège `/admin/*`, la page `/admin/utilisateurs` exige `isSuperAdmin`.
- **Pas de données préremplies / de seed** : le contenu est saisi par l'administrateur via l'application.
- Attente de l'utilisateur : livrer de **vraies fonctionnalités de gestion** (actions/CRUD/interrupteurs qui modifient l'état via l'API), pas seulement des pages d'affichage.

### Concession unique & contact

- CHCars est **une seule concession** : tous les véhicules sont à la même adresse. Pas de ville par annonce (`Listing.city`/`postal_code` retirés). Les coordonnées viennent des variables `env.COMPANY_*`, exposées par `GET /api/company` (public) et partagées côté front via `CompanyContext` / `useCompany()`. Liens réseaux sociaux du pied de page : `COMPANY_INSTAGRAM_URL` / `COMPANY_FACEBOOK_URL` (optionnels, `https://` uniquement, icône masquée si vide). N° de TVA : `COMPANY_VAT_NUMBER` (factures + `vatNumber` de `GET /api/company`, affiché en bas du pied de page, masqué si vide).
- Formulaire de contact public : `POST /api/contact` (exempt de CSRF, rate-limité, honeypot `website` que le service ignore silencieusement) → table `contact_message`. `GET`/`PATCH`/`DELETE /api/contact[/:id]` réservés à l'admin (page `/admin/messages`).

### Fiche détaillée d'une annonce (migration 008)

- Colonnes optionnelles de `listing` : `equipment` (JSON, clés de `entities/listingDetails.ts`), `euro_norm`, `co2` (g/km), `has_car_pass`, et la **garantie** : `warranty_months` (NULL = aucune), `warranty_kind` (`dealer` / `manufacturer`), `warranty_coverage` (JSON, éléments couverts choisis un à un), `warranty_notes` (conditions), `warranty_custom` (migration 012 : éléments couverts saisis librement, ≤ 15 × 60 car., dédoublonnés sans tenir compte de la casse). Formulaire : choix « Sans garantie / Avec garantie », puces + « Autre élément couvert ». `utils/listingWarranty.ts` : sans durée, type / éléments / conditions sont vidés ; type par défaut `dealer`. Réponses API : listes toujours en tableau (jamais `null`).
- Front : mêmes listes dans `types/listingDetails.ts`, libellés fr/en/nl (`t.details`). Formulaire admin : sections Équipements (puces), Environnement et documents, Garantie (durée rapide ou libre, type, éléments couverts avec raccourcis, conditions). Fiche : badges garantie / Car-Pass / Euro, carte Équipements par thème, carte Garantie, bouton Partager (`ShareButton` : partage natif, sinon WhatsApp / copier le lien), véhicules similaires (`utils/similarListings.ts`, testé), barre d'action collante sur téléphone (`ListingActionBar` : prix, Appeler, Réserver). Pas de financement / paiement par mensualités (choix de la concession).

### Réservations

- Table `reservation` (migrations 005 + 006), deux types sur une annonce **publiée** : `hold` (mise de côté) et `visit` (essai/visite à `visit_at`, 8 h–20 h heure de Paris, ≥ 1 h d'avance, ≤ 90 j — `utils/reservationRules.ts`). Statuts `pending` → `confirmed` | `declined` ; `pending`/`confirmed` → `cancelled`.
- **Compte obligatoire** : `POST /api/reservations` exige une session (rate-limité) ; identité copiée du compte + téléphone saisi. Côté front, un visiteur est envoyé directement sur `/connexion` et revient sur l'annonce formulaire ouvert : retour en `sessionStorage` (`utils/returnPath.ts` + `utils/reservationIntent.ts`), repris par la connexion / l'inscription (retour arrière dans l'historique si l'annonce est la page précédente, sinon `?reserver=hold|visit`) et par `ReturnAfterLogin` pour Google. `GET /reservations/mine`, `POST /reservations/:id/cancel` (propriétaire, page « Mon compte »).
- Admin : `GET`/`PATCH`/`DELETE /api/reservations[/:id]` (page `/admin/reservations`). Une seule mise de côté confirmée et en cours par annonce, vérifiée **sous verrou** (`pessimistic_write` sur la ligne `listing`) ; `GET /listings[/:id]` renvoie `reserved: true` tant qu'elle court (badge « Réservé »). E-mails client (fr/en/nl) à chaque étape, avis à `COMPANY_EMAIL` pour chaque nouvelle demande / annulation client.
- **Véhicule plus en vente** (vendu — facture ou statut manuel —, archivé, brouillon) avec des réservations **en cours** (`pending`, ou `confirmed` non échue — même règle front `utils/reservationAvailability.ts` / back `countOpenForListing`) : jamais d'annulation automatique, mais l'API refuse de **confirmer** (409) et de **supprimer l'annonce** (409, sinon la cascade effacerait les demandes sans prévenir le client) ; le front le signale partout — badge + bandeau + « Confirmer » masqué + refus prérempli (`/admin/reservations`), repère « N résa » et avertissement au changement de statut (`/admin/annonces`, fiche annonce), alerte sur le dossier de vente, badge « Véhicule vendu / Plus disponible » côté client.

### Stock du garage (migration 009)

- Tables `stock_vehicle` (+ `stock_vehicle_cost`), admin only (`/api/stock`, pages `/admin/stock`, `/admin/stock/nouveau`, `/admin/stock/<id>`) : registre des véhicules gérés par la concession, **indépendant des annonces** — modèle choisi dans le catalogue (marque vérifiée), version, VIN (unique, l'identifiant — pas de plaque : elle suit le propriétaire en Belgique, migration 010), caractéristiques, entrée (date, origine achat / reprise / dépôt-vente, fournisseur, prix d'achat, prix visé, emplacement), frais, sortie (date + motif). Statuts `incoming` / `in_stock` / `preparation` (à la main) → `sold` / `exited` (via `POST /stock/:id/exit`, `reopen` pour revenir). Référence interne `STK-0001` (`utils/stockRules.ts`, testé : prix de revient, marge potentielle, jours au garage, date du jour à Bruxelles).
- **Le véhicule est la référence technique** : lien facultatif vers une annonce (`listing_id`, unique). « Créer l'annonce » (`/admin/annonces/nouvelle?stock=<id>` ou le bloc « Partir d'un véhicule du stock ») préremplit l'annonce et la lie (`stockVehicleId` à la création, `POST /listings`). La fiche du véhicule signale les écarts avec son annonce (`utils/stockGaps.ts`, testé).
- **Parcours « véhicule d'abord »** : « Nouvelle annonce » commence par le choix du véhicule (cartes du stock au garage sans annonce + recherche marque / modèle / VIN / n° de stock, ou « Entrer un nouveau véhicule ») puis ne demande que le commercial (`ListingFormFields lockTechnical`, récapitulatif `StockVehicleSummary`) ; la modification d'une annonce liée verrouille aussi la technique. « Entrer un véhicule » : marque → modèle avec création à la volée (`CatalogModelField`) et option « Mettre en vente ensuite » (redirige vers `?stock=<id>`). Le véhicule porte aussi ses **options et documents** (équipements, norme Euro, CO₂, Car-Pass — migration 011, champs partagés `EquipmentFields`) ; créer ou modifier un véhicule recopie sa technique + options / documents sur son annonce (`services/stockSync.ts`, aussi à la création d'une annonce depuis le stock) ; l'annonce garde le commercial (titre, prix, catégorie, description, **garantie**, photos).
- **Synchronisation** : annonce passée « Vendue » à la main → son véhicule sort du stock (vente, date du jour) ; facture finale d'un dossier → le véhicule du dossier (`sale.stock_vehicle_id`), à défaut celui de l'annonce, sort en vente à la date du paiement (`markListingVehicleSold`). Suppression d'un véhicule refusée s'il figure sur un dossier de vente.
- **Photos = celles du véhicule** (migration 013, table `stock_vehicle_image`, même traitement WebP + vignette, clés `stock/<id>/…`) : demandées à l'entrée du véhicule (`PhotoPicker`, au moins une si « Mettre en vente ensuite »), gérées sur sa fiche (`ListingImagePanel` + `stockGallery`, routes `/api/stock/:id/images`). Une annonce liée **affiche les photos de son véhicule** : `toListingResponse` les prend sur `listing.stockVehicle.images` (relation inverse chargée par les dépôts annonces / favoris / réservations, jamais renvoyée telle quelle) et `GET /listings/:id/images` aussi ; « Nouvelle annonce » ne demande plus de photos. Une annonce sans véhicule garde ses propres photos (`listing_image`). Suppression d'un véhicule = suppression de ses fichiers. `FUEL_TYPES` / `TRANSMISSIONS` vivent dans `entities/vehicleTypes.ts` (cycle d'import Listing ↔ StockVehicle).
- **Statuts annonce ↔ véhicule** (`utils/stockListingRules.ts`, testé ; même règle front `listingStatusBlock`) : une annonce liée n'affiche **que** les photos de son véhicule (jamais de mélange) ; lier une annonce qui a ses propres photos les **transfère** au véhicule (`adoptListingPhotos`, mêmes fichiers) ; sortie du véhicule → annonce `sold` (vente) ou `archived` (autre motif) ; remise en stock → annonce `published` si elle l'a déjà été, sinon `draft` ; annonce `sold` → `published` / `draft` remet le véhicule en stock ; **refusé (409)** : publier si le véhicule est sorti, remettre en vente / en stock un véhicule **facturé** (dossier `paid`), créer une annonce depuis un véhicule sorti, supprimer un véhicule qui a une annonce (le détacher d'abord).
- Dossier de vente : sélecteur unique `VehiclePicker` (stock au garage + annonces non portées par un véhicule ; recherche marque / modèle / VIN / n° de stock / année, clavier ↑ ↓ Entrée) qui remplit la ligne, le VIN et les liens.

### Facturation (dossiers de vente)

- Tables `sale`, `sale_line`, `sale_payment`, `sale_document`, `document_counter` (migration 007), admin only (`/api/sales`, page `/admin/ventes`). Acheteur saisi à la main (**aucun lien avec les comptes**), annonce optionnelle (`listing_id`).
- Les **paiements pilotent le dossier** (`utils/saleRules.ts`, calculs en centimes) : avance sur un brouillon → bon de commande `BC-AAAA-NNNN` (`ordered`) ; total atteint → facture `F-AAAA-NNNN` (`paid`) + annonce liée `sold` ; paiement intégral d'emblée → facture directe. Tout dans **une transaction** avec la ligne `sale` verrouillée ; numéro réservé par `INSERT … ON DUPLICATE KEY UPDATE` sur `document_counter` (continu, sans trou ; rendu si rollback, le fichier PDF est alors supprimé).
- Documents **figés** : `sale_document` garde numéro, montants et `storage_key` ; dossier non modifiable dès le 1er document ; paiement supprimable seulement si aucun document ne s'y rattache (`document_id`). Pas de suppression d'un dossier qui a des documents (FK `RESTRICT`).
- **Traçabilité** : un dossier s'affiche par sa référence métier (`saleReference` : n° de facture, sinon de bon de commande, sinon « Brouillon » — l'id ne sert qu'à l'adresse). Fichier téléchargé : `<numéro>_<véhicule>_<acheteur>.pdf` (`documentFilename`, à partir de la 1re ligne et de l'acheteur, figés dès le 1er document). Page Facturation en trois vues : **Dossiers** (filtrable par n° de document, client, véhicule, annonce ou VIN — `saleMatches`), **Factures** et **Bons de commande** — deux registres séparés (`SaleDocumentRegister`, `documentRegister` testé : un document par ligne, n° décroissant, groupé par mois avec sous-total, filtre par année, totaux, PDF ; numéros en pastilles `DocumentChip`, statut `SaleStatusPill`, barre d'encaissement par dossier ; un bon de commande indique la facture qui l'a soldé, une facture son bon de commande) ; la **facture PDF cite son bon de commande** (« Réf. bon de commande », et l'acompte dans les paiements reçus) ; chaque annonce admin (liste + fiche) liste ses dossiers (`salesByListing`). **Une annonce figurant sur un bon de commande ou une facture ne peut pas être supprimée** (409, `documentNumbersForListing`) : l'archiver, sinon `sale.listing_id` passerait à NULL.
- PDF par `services/pdf/saleDocumentPdf.ts` (`pdfkit`, polices standard Latin-1), stockés via `documentStorage` dans `env.DOCUMENTS_DIR` — **privé** (volume `documents`, jamais servi par nginx), téléchargé par `GET /api/sales/:id/documents/:documentId/pdf`. Mentions vendeur : `COMPANY_*` + `COMPANY_VAT_NUMBER` / `COMPANY_IBAN` / `COMPANY_BIC`.

Réponses API cohérentes :
- succès : `{ "success": true, "data": ... }`
- erreur : `{ "success": false, "message": "...", "details"?: ... }`

Vérification : `npm run typecheck` puis `npm run build`.

### Sécurité (à préserver)

- `app.ts` : `helmet` (CSP `default-src 'none'`, HSTS en prod, CORP `same-site`), CORS restreint à `env.CORS_ORIGIN` (méthodes/headers explicites), corps JSON limité à 32 kB, `hpp`, `x-powered-by` désactivé, `trust proxy` = `env.TRUST_PROXY`.
- Rate limiting (`middlewares/rateLimit.ts`) : général 1000/15 min sur toute l'API (sauf `POST /analytics/pageview`, limiteur propre 200/15 min), strict 10/15 min sur `/auth/register` et `/auth/login` (et sur `/auth/reset-password`), 5/15 min sur `/auth/forgot-password`.
- Mesure d'audience interne (table `page_view`, migration 003) : le front (`PageViewTracker`) n'envoie `POST /api/analytics/pageview` qu'après consentement, et le back n'enregistre que si la requête porte le cookie `chcars_visitor_id` (UUID aléatoire) ; jamais l'admin, ni IP, ni user-agent, ni query string ; purge > 13 mois au démarrage puis chaque jour. Stats : `GET /api/analytics/summary?days=7|30|90` (admin) → page `/admin/statistiques`.
- JWT : algorithme épinglé à `HS256` (signature **et** vérification) ; `JWT_SECRET` ≥ 32 caractères imposé par `env.ts`.
- **Authentification par cookie** : `auth.controller` pose le JWT dans un cookie `chcars_token` **httpOnly** (jamais dans le corps de réponse) + un cookie lisible `chcars_csrf` (`utils/cookies.ts`). `authenticate` lit le cookie (repli sur `Authorization: Bearer` pour l'outillage). `POST /auth/logout` efface les cookies.
- **CSRF** : double-submit (`middlewares/csrf.ts`) — `ensureCsrfCookie` garantit le cookie, `verifyCsrf` exige l'en-tête `X-CSRF-Token` = cookie sur toute requête non-GET, sauf `/auth/login`, `/auth/register`, `/auth/forgot-password` et `/auth/reset-password`. CORS avec `credentials: true` et origine unique.
- **Double authentification (TOTP) obligatoire pour `admin` / `super_admin`** (et tout compte l'ayant activée) : `POST /auth/login` ne pose alors pas la session mais un cookie httpOnly `chcars_mfa` (JWT `typ: mfa_pending`, 5 min) ; `POST /auth/mfa/setup` (1er enrôlement : secret + URI `otpauth://`) puis `POST /auth/mfa/verify` (code TOTP ou code de secours) posent la session, dont le JWT porte `mfa: true`. `authenticate` refuse toute session admin sans ce claim. Tables `user_mfa` (secret chiffré AES-256-GCM via `MFA_ENCRYPTION_KEY`, anti-rejeu `last_used_step`, verrouillage 5 échecs → 15 min) et `user_recovery_code` (SHA-256, usage unique). TOTP implémenté sans dépendance (`utils/totp.ts`, vecteurs RFC testés). Réinitialisation : `npm run reset-mfa -- --email=…`.
- **Connexion Google (OpenID Connect)**, optionnelle (`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_REDIRECT_URI`, sinon `GET /auth/providers` → `google: false` et bouton masqué). Flux code + PKCE côté serveur, sans dépendance (`utils/googleOAuth.ts`) : `GET /auth/google` pose un cookie httpOnly signé `chcars_oauth` (state + nonce + verifier, 10 min, `SameSite=Lax`) et redirige vers Google ; `GET /auth/google/callback` vérifie `state`, échange le code, valide les claims de l'ID token (iss, aud, exp, nonce, `email_verified`), puis redirige vers le front (`/<locale>`, `/<locale>/connexion?mfa=enroll|code` si 2FA due, `?google=<raison>` en cas d'échec). Compte retrouvé par `user.google_sub`, sinon rattaché au compte de même e-mail (refus si déjà lié à un autre compte Google), sinon créé en `user` **sans mot de passe** (`password_hash` NULL → connexion par mot de passe refusée). Un admin passe toujours par la 2FA.
- **Mot de passe oublié** (lien sur la page de connexion, seul moyen de changer de mot de passe) : `POST /auth/forgot-password` (réponse 202 identique que le compte existe ou non, traitement en arrière-plan, cooldown 2 min par compte, limiteur 5/15 min par IP) envoie par e-mail un lien `/<locale>/reinitialiser-mot-de-passe?token=…` — jeton 256 bits, seule son empreinte SHA-256 est stockée (`password_reset_token`, migration 004), 30 min, usage unique consommé dans la même transaction que la mise à jour du mot de passe. `POST /auth/reset-password` n'ouvre pas de session et pose `user.password_changed_at` : `authenticate` refuse tout JWT dont `iat` est antérieur (déconnexion de tous les appareils) ; avis par e-mail. E-mails via `services/mail/` (nodemailer, SMTP **Brevo** `SMTP_*` / `MAIL_FROM`) ; sans `SMTP_HOST` : console en dev/test, rien en prod (lien jamais journalisé).
- Login à temps constant (`auth.service.ts` : bcrypt toujours exécuté, hash factice si l'e-mail est inconnu) ; bcrypt en 12 tours.
- Recherches : `escapeLike()` sur toute valeur passée à `Like(...)`.
- `errorHandler` : jamais de stack ni de message interne au client en production.
- Validation d'entrée : schémas zod `.strict()` (rejet des clés inconnues).
- Frontend : en-têtes via `next.config.ts` (`X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS, `poweredByHeader: false`) et CSP via `proxy.ts` (le « middleware » Next 16 ; stricte + nonce en production, permissive en dev pour le HMR). `apiClient` envoie `credentials: "include"` et l'en-tête `X-CSRF-Token` sur les requêtes mutantes.

### Images

Les photos sont rattachées à l'**annonce** (`ListingImage`, route imbriquée `/api/listings/:listingId/images`). Upload en `multipart/form-data` (champ `file`), admin only : `multer` (mémoire) → validation via `sharp().metadata()` (JPEG / PNG / WebP ; **HEIC iPhone** reconnu à sa marque `ftyp` et décodé par `heic-decode` — libheif en WebAssembly, le libvips précompilé de sharp ne lit pas le HEVC — `utils/heic.ts`, testé, taille vérifiée avant décodage) → ré-encodage **WebP ≤ 2000 px** + vignette 400 px (`imageProcessor`), EXIF supprimée. Les fichiers vont sur disque via `StorageService` (`LocalDiskStorage`, dossier `env.UPLOAD_DIR`) ; la base ne stocke que `storage_key` + métadonnées. L'URL publique est reconstruite à partir de `env.PUBLIC_UPLOADS_URL`. Supprimer une annonce efface aussi ses fichiers (`listingImageService.purgeForListing`).

### Base de données

- `synchronize` et `migrationsRun` sont **toujours** à `false` dans `data-source.ts` — l'app ne touche jamais au schéma au runtime.
- Le schéma vit dans des **migrations versionnées** `back/db/migrations/NNN_description.sql` (`001_init.sql` = schéma initial). `npm run migrate` (`src/scripts/migrate.ts`, connexion `mysql2` directe, ciblé par `NODE_ENV`, verrou `GET_LOCK`) applique dans l'ordre celles qui manquent et les enregistre dans `schema_migrations` (avec empreinte SHA-256) ; il s'arrête à la première erreur. `deploy.sh` le lance à chaque déploiement, **précédé d'une sauvegarde** (`mariadb-dump` → `backups/<date>_<tag>.sql.gz` dans le dossier de déploiement, rotation `BACKUP_KEEP` = 10 par défaut ; déploiement arrêté si le dump échoue). Restauration : `README.md` § « Sauvegardes de la base ».
- **Ne jamais lancer de commande destructive** (`DROP`, `TRUNCATE`, `DELETE` massif) sur la base sans demande explicite de l'utilisateur.
- À chaque changement de schéma : **ajouter un nouveau fichier** de migration (numéro suivant), puis `npm run migrate`. **Ne jamais modifier une migration déjà appliquée** (empreinte vérifiée, le script refuse). Les entités TypeORM doivent rester alignées sur le résultat.
- La création de la **base** et de l'**utilisateur** MariaDB reste manuelle (hors périmètre du script).

## CI/CD (`.github/workflows/`, `deploy/`, `e2e/`)

Pipeline `ci-cd.yml` : tests back + front → build Docker → GHCR (`chcars-back` / `chcars-front`, tag `sha-<commit>`) → déploiement préprod → Playwright E2E (`e2e/`) → **approbation manuelle** (Required reviewers sur l'environnement GitHub `production`, notification e-mail) → production → job `release` (tag `vX.Y.Z` + GitHub Release ; patch par défaut, `#minor` / `#major` dans un message de commit pour monter plus haut). `deploy.yml` est le workflow réutilisable (et lançable à la main pour un rollback) : SSH + `deploy/deploy.sh` (`docker compose`, MariaDB ; reverse proxy = **nginx du serveur**, `deploy/nginx/chcars.conf` + certbot, installé à la main — les conteneurs n'écoutent que sur `127.0.0.1`, préprod et prod sur **le même serveur** : un dossier, un `.env` et un `COMPOSE_PROJECT_NAME` chacun (vérifié par `deploy.sh`), ports serveur prod 3010/3011/3012 et préprod 3013/3014/3015 via `FRONT_PORT` / `BACK_PORT` / `DB_HOST_PORT`, un site nginx par environnement généré depuis le modèle `deploy/nginx/chcars.conf`). Détails et mise en place : `README.md` § « CI/CD et déploiement ».

- **Une seule image par commit**, promue de la préprod à la prod : rien de spécifique à un environnement ne doit être figé au build. Le front est construit avec `NEXT_PUBLIC_API_URL=/api` (même origine derrière nginx) ; tout le reste passe par le `.env` du serveur.
- `e2e/` est un package de tests indépendant (pas une 3ᵉ application) ; il ne vise que des environnements déployés, jamais la prod (création de comptes de test).
- Le back est compilé via `tsconfig.build.json` (exclut les `*.test.ts`) ; `migrate` / `createAdmin` tournent dans le conteneur via `node dist/scripts/*.js`.
- Le front est en `output: "standalone"` (requis par `front/Dockerfile`).
